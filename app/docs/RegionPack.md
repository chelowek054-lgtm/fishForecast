# Пакет района: формат обмена и будущее API

## Зачем понадобился

Обмен картами был устроен так: наружу уезжала база тайлов MapLibre целиком.
Сотни мегабайт, все районы разом — и ни слова о том, что рыболов про эти
места знает. Норма давления, глубины, точки и справочник видов оставались
дома, получатель видел голый прямоугольник и сам догадывался, зачем ему его
прислали. Вдобавок так раздавались чужие тайлы, чего лицензии источников
не разрешают.

Пакет устроен наоборот: это **знание о месте**, а не картинка. Тайлы в него
не входят — получатель докачает их сам по границам района при первой сети.
Файл выходит в килобайтах, его можно отправить в мессенджере, и он читается
глазами.

Тот же документ примет и вернёт будущий общий сервер: формат сразу
рассчитан на то, что районы будут публиковаться и приходить от разных людей.

## Что внутри

Файл `*.ffpack` — это JSON. Схема: `fishforecast.region-pack/3`.

| Раздел | Что несёт | Почему это знание о месте |
|---|---|---|
| `region` | Границы, масштабы, норма давления, высота, тип водоёма, глубины мели и ямы | Норма посчитана по наблюдениям за эту точку, а тип и глубины знает только тот, кто там ловит |
| `spots` | Точки: берег или вода, структуры места, кто здесь берёт | Где встать и куда бросать — разные вещи, а структуры и есть то, чем место отличается от соседнего |
| `fish` | Виды, которые здесь берут: пороги, наживки, правила прикормки | В разных водоёмах берёт разная рыба, и чем её кормить — такое же знание о месте, как глубина |
| `author` | Случайный идентификатор и, по желанию, имя | В общей базе важно видеть, чей район; учётной записи ради файла не требуется |

Пример:

```json
{
  "schema": "fishforecast.region-pack/3",
  "id": "9f2c…",
  "createdAt": "2026-08-27T12:00",
  "author": { "id": "b71a…", "name": "Рыболов" },
  "region": {
    "id": "region-1",
    "name": "Озеро",
    "bounds": { "north": 55.8, "south": 55.7, "east": 37.7, "west": 37.6 },
    "minZoom": 10.0, "maxZoom": 14.0,
    "normalPressureMmHg": 745.8,
    "elevationM": 152.0,
    "waterBodyType": "still_small",
    "shallowDepthM": 1.5, "deepDepthM": 5.0
  },
  "spots": [
    {
      "id": "spot-1", "name": "Мысок", "lat": 55.78, "lon": 37.62,
      "placement": "SHORE", "fishId": "fish-carp",
      "structures": ["drop_off", "reeds"]
    }
  ],
  "fish": [
    {
      "id": "carp", "name": "Карп / Сазан",
      "temp": { "opt_min": 18, "opt_max": 26, "abs_min": 8, "abs_max": 30 },
      "pressure": { "min_mmHg": 740, "max_mmHg": 755 },
      "oxygen": { "comfort_mg_l": 5.0, "critical_mg_l": 3.0 },
      "default_horizon": "bottom", "cold_temp_threshold": 14.0,
      "baits": { "cold": ["Мотыль"], "warm": ["Кукуруза"] },
      "groundbait_rules": { "warm": { "volume": "high", "sweetness": "high" } }
    }
  ]
}
```

## Идентификаторы

Числовой ключ Room у каждого устройства свой: два рыболова, у каждого свой
«район номер один», при обмене затирали бы друг друга. Поэтому у района,
точки и вида есть собственный глобальный `uid` (UUID), и именно он ездит в
пакете. Он же станет ключом в общей базе — записи не
придётся перезаводить, когда появится сервер.

Ссылки внутри пакета тоже глобальные: точка ссылается на вид по `uid`, а не
по числу, иначе у получателя она указала бы на случайную рыбу.

## Правила слияния

Одно правило на всё содержимое: **совпал `uid` — это та же запись**, что бы
ни было написано в имени.

| Что | Если известно | Если ново |
|---|---|---|
| Район | Обновляются знания о месте; своя скачанная область, её размер и свой замер воды остаются — это про устройство, а не про место | Заводится, тайлы качаются при первой сети |
| Точка | Обновляется, числовой ключ сохраняется | Заводится |
| Вид рыбы | **Не перезаписывается**: справочник рыболов правит под себя | Заводится |

Отдельно про пороги видов: чужие цифры не должны молча менять расчёт клёва
на своих водоёмах. Поэтому известный вид остаётся как есть, а привязка
чужой точки просто указывает на него.

Раздел `fish` — это тот же документ, которым описан общий справочник видов
(`fishforecast.fish-catalog/1`). Двух описаний одной и той же рыбы быть не
должно: что приходит с сервера, что едет в пакете района — один формат.
Из-за этого схема пакета и перешла со `/1` на `/2`.

## Версии схемы

Читатель проверяет схему до разбора. Незнакомые поля игнорируются — пакет,
собранный более новой сборкой того же поколения, читается. Смена поколения
(`/2`) отвергается с понятным сообщением: молча завести район с половиной
данных хуже, чем отказаться.

## Почему без тайлов

1. Файл остаётся в килобайтах и уходит любым мессенджером.
2. Не раздаются чужие тайлы — политика источника схемы предзагрузку и
   передачу не разрешает, это отмечено в README как условие публикации.
3. Границы района в пакете есть, значит скачать тайлы получатель может сам —
   ровно те же и по тем же правилам, что и любой другой район.

Цена решения: без сети чужой район не открыть. Это честный размен, и
приложение говорит об этом прямо при импорте.

## Будущий сервер: набросок API

Формат уже готов к тому, чтобы стать телом запроса. Ничего из этого пока не
реализовано — раздел существует, чтобы не проектировать формат дважды.

> Полный контракт платформы, включая эти эндпойнты, ведётся отдельно:
> [architecture/server/api/openapi.yaml](architecture/server/api/openapi.yaml),
> правила версионирования и ошибок —
> [architecture/server/api/contracts.md](architecture/server/api/contracts.md).

| Метод | Что делает | Тело |
|---|---|---|
| `POST /v1/regions` | Опубликовать район | `RegionPack` |
| `PUT /v1/regions/{uid}` | Новая версия своего района | `RegionPack` |
| `GET /v1/regions?bbox=&q=` | Искать районы по охвату и названию | — |
| `GET /v1/regions/{uid}` | Забрать район целиком | → `RegionPack` |
| `GET /v1/regions/{uid}/catches` | Уловы района (когда появятся) | → `CatchPack` |
| `POST /v1/regions/{uid}/catches` | Поделиться уловом из точки | `CatchPack` |

Что придётся решить на сервере, а не в файле:

- **Права.** Менять район может тот, кто его опубликовал; остальные
  предлагают изменения — иначе первый же спорщик перепишет чужие глубины.
- **Слияние версий.** Правило `uid` работает и здесь, но нужен счётчик
  версий у района: побеждает не «последний записавший», а тот, кто писал
  поверх актуальной версии.
- **Приватность.** Точки — это секреты, ради которых приложение и делалось.
  Публикация обязана быть отдельным осознанным действием, с выбором, какие
  точки уходят, а какие остаются дома.
- **Модерация и доверие.** В общей базе появятся и мусор, и выдумка. Нужен
  хотя бы вес автора: сколько его районов подтверждено чужими уловами.

## Чего в пакете пока нет

- **Уловы из журнала.** Это личные данные, им нужен отдельный выбор при
  отправке и собственный раздел схемы (`CatchPack` в наброске выше).
- **Фотографии.** Тяжёлые и личные; когда понадобятся, пакет станет ZIP с
  тем же `manifest.json` внутри и вложениями рядом.
- **Тайлы.** См. выше — сознательно.

## Почему зон больше нет

Обводка контуров была: рыболов ставил вершины по карте, получал зону и мог
нарезать её секторами. Знание из этого не выходило. Расчёт клёва считает
место по структурам — коряжник, бровка, приток, — и берёт их у точки, а не
у площади пятна. Зона оставалась картинкой: её надо было рисовать пальцем,
хранить, переносить между устройствами и объяснять на сервере, ничего за это
не получая.

Осталась точка. Она отвечает на те же вопросы короче: `placement` говорит,
берег это или вода, `structures` — что там за место, `fishId` — кто здесь
берёт. Разговор секторами («взял в третьем») точка тоже переносит: сектор
это её имя, а не отдельная сущность.

Формат при этом остался в поколении `/3`. Пакеты, собранные со старыми
зонами, читаются: незнакомый раздел игнорируется, а точки приезжают как
приезжали. Ломать поколение ради того, чего в пакете больше нет, значило бы
отвергать чужие файлы без всякой пользы.

## Совместимость со старым обменом

Обмен точками через GPX остался: он про совместимость с другими
приложениями, а не про знание о месте. Передача базы тайлов целиком
убрана — вместе с кодом слияния чужих баз MapLibre.

## Справочник видов: `fishforecast.fish-catalog/1`

Тот же подход, что у пакета района, но для общего знания о рыбе. Документ
лежит в ассетах (`initial_fish.json`) и может приходить с сервера по адресу,
который задаёт рыболов.

Вид описывается так:

```json
{
  "id": "burbot",
  "name": "Налим",
  "temp": { "opt_min": 2, "opt_max": 12, "abs_min": 0, "abs_max": 15 },
  "pressure": { "min_mmHg": 740, "max_mmHg": 760 },
  "oxygen": { "comfort_mg_l": 6.0, "critical_mg_l": 4.0 },
  "default_horizon": "bottom",
  "cold_temp_threshold": 12.0,
  "baits": { "cold": ["Выползок"], "warm": ["Не клюёт"] },
  "groundbait_rules": {
    "cold": { "volume": "low", "fraction": "coarse", "sweetness": "none",
              "flavor_profile": "fish_blood", "notes": "…" }
  }
}
```

Почему поля именно такие:

- **Два температурных диапазона.** Рыба не выключается на границе: в
  оптимуме она кормится, между оптимумом и пределом активность тает, за
  пределом её нет. Ширина этого перехода у видов разная, и общей константой
  её не задать.
- **Пороги кислорода у вида.** Карасю хватает трёх миллиграммов на литр,
  налиму нужно шесть. Общая шкала уравняла бы их и соврала бы про обоих.
- **Порог холодного стола.** Ниже него — животные насадки и мало корма,
  выше — растительные и сладкие ароматы.
- **Коды, а не переводы.** `low`, `sweet_fruity` остаются кодами: документ
  ходит между устройствами и сервером, а перевод — дело экрана.

Файл бывает двух видов: голым массивом — так его удобно править руками — и
обёрнутым в объект с `version`, как отдаёт сервер. Версия сравнивается до
записи: качать одно и то же при каждом открытии экрана незачем.

Правила слияния такие же, как у пакета: вид узнаётся по `id`. Своё
описание вида и виды, заведённые рыболовом вручную, обновление не трогает.
Записи, заведённые до появления общего справочника, находятся по имени —
иначе после первого же обновления рыболов получил бы двух щук.

| Метод | Что делает | Тело |
|---|---|---|
| `GET <адрес справочника>` | Забрать справочник целиком | → `FishCatalog` |

Отдельного эндпойнта пока нет намеренно: справочник — статический файл, его
можно держать хоть в репозитории проекта, хоть на своём хостинге, и это
работает уже сейчас.
