# Наблюдаемость и разбор инцидентов

Как понять, что происходит в системе, не читая код. Документ задаёт стандарт
логирования и метрик и описывает разбор типовых поломок.

## Сквозной идентификатор

Каждый поток данных имеет `X-Correlation-Id`:

1. Клиент рождает его на действие пользователя (одно действие — один
   идентификатор, даже если оно превратится в пять запросов).
2. Шлюз принимает заголовок; если его нет — создаёт свой и возвращает в ответе.
3. Идентификатор кладётся в контекст запроса и попадает **в каждую** строку лога,
   в задачу для воркера и в сообщение WebSocket.
4. Клиент пишет его рядом с ошибкой, которую показывает человеку. Скриншот с
   ошибкой становится входом в логи.

Без этого правила разбор жалобы «не загрузился район» превращается в гадание.

## Логи

Структурные, одной строкой JSON, в поток вывода:

| Поле | Пример | Обязательно |
|---|---|---|
| `ts` | `2026-08-29T10:12:03.412Z` | Да |
| `level` | `info`, `warn`, `error` | Да |
| `msg` | `region published` | Да |
| `correlation_id` | `01J9...` | Да |
| `user_id` | UUID или `anonymous` | Да |
| `route` | `POST /v1/regions` | Для запросов |
| `status` | `201` | Для запросов |
| `duration_ms` | `84` | Для запросов и задач |
| `entity` | `region:9f2c...` | Где применимо |

Чего в логах не бывает никогда: токенов, содержимого сообщений, точных координат
точек, фото. Координаты логируются с точностью до района.

## Метрики

По каждому эндпойнту — частота, доля ошибок, длительность (95-й и 99-й
процентили). По каждому ресурсу — загрузка, насыщение, ошибки.

Отдельно то, что говорит о смысле, а не о технике:

| Метрика | Зачем |
|---|---|
| Доля клиентов на актуальной версии знаний | Дошёл ли выпуск до людей |
| Возраст самой старой операции в очередях клиентов | Работает ли синхронизация вообще |
| Конфликты версий районов в сутки | Не сломались ли правила слияния |
| Время обработки промера | Не встала ли очередь воркеров |
| Отношение уловов к пустым выездам | Здоровье датасета: одни успехи — смещённая выборка |
| Доля публикаций, отклонённых проверкой | Не отвергаем ли живых людей |

## Трассировки

Запрос → задача в очереди → воркер → база. Один идентификатор трассировки на
поток, тот же, что и correlation-id. Смотреть в первую очередь: публикация
района, синхронизация пачкой, обработка промера, публикация версии знаний.

## Алерты

| Условие | Срочность | Первое действие |
|---|---|---|
| Доля 5xx выше 2% пять минут | Немедленно | Смотреть последние выкладки, откатить |
| Очередь задач растёт полчаса | В течение часа | Проверить воркеры и внешние сервисы |
| Публикация знаний не доходит до клиентов сутки | В течение дня | Проверить раздачу и CDN |
| База: место меньше 20% | В течение дня | Чистка витрины датасета, расширение |
| Ошибки записи в объектное хранилище | Немедленно | Публикации и фото ломаются молча |

## Типовые разборы

**«Не приехали новые словари».** Проверить: версия опубликована и в состоянии
`published`; документ лежит в хранилище и отдаётся; ответ не `304` из-за
неверного ETag; на клиенте не задан свой адрес источника. Клиент при негодном
документе молча остаётся на встроенном — в логах это видно по ошибке проверки
схемы.

**«Точки задвоились».** Значит, разошлись `uid`: запись создана дважды с разными
идентификаторами. Смотреть очередь исходящего клиента и ключи идемпотентности за
период. Правило «совпал uid — та же запись» нарушается только при потере uid.

**«Улов ушёл в ленту, хотя не должен».** Проверить `visibility` записи и путь,
которым она попала на сервер. Публикация возможна только явным действием;
несоответствие — это дефект, а не настройка.

**«Промер завис в обработке».** Смотреть состояние набора и логи воркера по
correlation-id загрузки. Файл с миллионом точек — нормальная причина; отсутствие
свободной памяти — нет.

**«Клиент не может синхронизироваться после обновления сервера».** Проверить, не
сломан ли контракт: удалённое поле или ужесточённая обязательность. Старая сборка
обязана работать — это требование, а не любезность.

## Что считается инцидентом

Недоступность API дольше пяти минут, потеря пользовательских данных в любом
объёме, утечка личного (точки, сообщения, контакты), публикация версии знаний,
ломающей расчёт. Последнее чинится откатом версии — это самый быстрый способ
вернуть людям работающее приложение.
