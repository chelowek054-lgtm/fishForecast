# ADR-0010. Documentation Driven Development: документ ведёт код

**Статус:** принят · 2026-08-30

## Контекст

Комплект артефактов написан, но сам по себе он ничего не гарантирует. Документы,
которые правят после кода, за пару месяцев превращаются в отчёт о прошлом:
читать их можно, полагаться нельзя. Дальше архитектор теряет контроль ровно в тот
момент, когда думает, что он у него есть.

Отдельное обстоятельство: значительную часть кода пишет языковая модель. Она
быстрее человека и охотно делает больше запрошенного — и именно поэтому ей нужна
точка, где работа останавливается и сверяется с намерением. Код, написанный за
минуту, ревьюится дольше, чем правка документа, которую видно целиком.

## Решение

Порядок работы в проекте называется **Documentation Driven Development (DocDD)**:
изменение начинается с документа, документ подтверждает человек, и только после
подтверждения пишется код.

Аббревиатура намеренно `DocDD`, а не `DDD`: последнее занято Domain-Driven Design,
и путать их не стоит.

Цикл:

```
намерение → правка документа → подтверждение человеком → код → сверка
```

Правило для агента записано в `CLAUDE.md` в корне репозитория — том файле,
который читается в начале каждой сессии.

## Что считается изменением, требующим документа

| Меняется | Документ |
|---|---|
| Границы системы, инварианты, стек | `00-manifest.md` |
| Пользовательский сценарий | `01-user-flows.md` |
| Состав компонентов и связи | `02-containers.md`, `client/overview.md`, `server/overview.md` |
| Куда ходят данные | `03-dataflow.md` |
| Схема базы, поле, приватность, срок хранения | `04-data-dictionary.md` |
| Формат запроса или сообщения | `openapi.yaml`, `asyncapi.yaml` |
| Порядок шагов в сложном процессе | `05-sequences.md` |
| Новое требование или способ его проверки | `06-traceability.md` |
| Состав работ фазы | `07-phases.md` |
| Выбор между вариантами с последствиями | новый ADR |

## Исключения

Документ не правится, если поведение не меняется: опечатки, форматирование,
переименование внутренней переменной, ускорение без смены результата.

Починка дефекта — тоже исключение, но с оговоркой: если дефект возник потому, что
код никогда не делал описанного, правится код. Если выяснилось, что документ
описывал не то, что задумано, — сперва правится документ.

Явная просьба человека сделать сразу отменяет правило на одно изменение. Это его
право; агент не спорит, но и не пользуется исключением сам.

## Последствия

- Крупная работа начинается с обсуждаемого текста, а не с обсуждаемого диффа.
  Развернуть направление на этом этапе стоит минуты.
- Документация не отстаёт по устройству процесса, а не по дисциплине.
- Скорость мелких правок падает — это принимается. Мелкие правки редко бывают
  теми, где теряется архитектура.
- Появляется явная точка подтверждения: до неё ответственность на агенте, после —
  решение принято человеком.

## Отвергнуто

**Писать документацию после кода.** Проверено практикой отрасли: она отстаёт
всегда, а не иногда.

**Генерировать документацию из кода.** Работает для сигнатур и не работает для
причин. «Почему так» из кода не выводится, а именно это и нужно архитектору.

**Полагаться на ревью.** Ревью ловит ошибки в реализации, а не расхождение с
замыслом: к моменту ревью замысел уже воплощён и защищается автором.
