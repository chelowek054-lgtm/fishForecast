# ADR-0008. Разделение на Gradle-модули по слоям знания

**Статус:** принят · 2026-08-29

## Контекст

Проект — один модуль `:app`, границы держатся на дисциплине пакетов. Это уже
подводит: `domain/fish/FishCatalog.kt` импортирует сущность Room ради
отображения, то есть формат обмена знает о базе. С появлением сервера и админки
часть кода становится общим знанием, и его нельзя оставлять в одной куче с UI.

## Решение

Модули: `:core-domain`, `:core-knowledge`, `:core-bitescore`, `:core-ffpack`,
`:data`, `:feature-*`, `:app`. Все `:core-*` — чистый Kotlin без Android и без
Room. Отображение «документ ↔ строка базы» живёт в `:data`.

## Последствия

- Нарушить границу становится нельзя технически, а не по договорённости.
- Тесты ядра запускаются без эмулятора и быстрее.
- Переезд делается **без изменения поведения**: разделение и правка логики в
  одном изменении не разбираются.
- Сборка усложняется, время холодной сборки растёт; инкрементальная — падает.

## Отвергнуто

**Оставить один модуль и договориться.** Договорённость уже нарушена в одном
месте; со временем нарушений станет больше.

**Kotlin Multiplatform ради общего кода с сервером.** Сервер на Python по
решению о ML-части; тянуть JVM-сервис только ради общей формулы дороже, чем
держать общие данные и тест-векторы.
