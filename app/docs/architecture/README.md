# Архитектурный комплект FishForecast

Здесь лежит то, по чему система строится и проверяется: границы, потоки данных,
контракты и решения с их причинами. Код — следствие этих документов, а не
наоборот.

Комплект появился, когда приложение перестало быть одним Android-клиентом. К нему
добавляются сервер, админка базы знаний, социальная часть и слой глубин, и
решения теперь принимаются на уровне границ и потоков, а не по месту в коде.

## Правила ведения

0. **Документ ведёт код (DocDD).** Изменение начинается с правки документа,
   правка подтверждается человеком, и только после этого пишется код. Порядок
   называется Documentation Driven Development и описан в
   [adr/0010](adr/0010-documentation-driven-development.md); правило для агента
   лежит в [CLAUDE.md](../../../CLAUDE.md). Остальные правила — следствия этого.
1. **Схемы как код.** Все диаграммы — mermaid внутри markdown, в git рядом с
   кодом. Картинок из внешних редакторов в комплекте нет: их нельзя ни
   отревьюить, ни обновить в том же изменении.
2. **Сначала контракт, потом код.** Новый эндпойнт или сообщение появляется
   сначала в `openapi.yaml` / `asyncapi.yaml`. Код, разошедшийся с контрактом,
   считается сломанным, а не «опережающим документацию».
3. **Документ меняется тем же изменением, что и код.** Правка потока данных без
   правки схемы — незакрытая работа.
4. **Сквозной идентификатор.** Каждый запрос несёт `X-Correlation-Id`, и по нему
   поток восстанавливается в логах целиком — см. [server/runbook.md](server/runbook.md).
5. **Отказ лучше тихой порчи.** Любой входящий документ проверяется по схеме до
   применения; несовпало поколение — отказ с понятной причиной. Это правило уже
   действует в коде клиента и распространяется на сервер.
6. **Язык — русский**, тон как в остальных документах проекта: объяснять
   «почему», а не пересказывать «что».
