Roadmap разработки приложения для анализа клёва (Android, Kotlin)

Общее описание

Приложение предназначено для локального анализа вероятности клёва рыбы на основе выбранного вида рыбы, водоёма (геолокация) и погодных условий (давление, ветер, температура). Работает преимущественно офлайн, периодически обновляет прогноз погоды и картографические данные. Пользователь может добавлять и редактировать виды рыб, загружать недельный прогноз погоды и офлайн-карты.



Технологический стек (рекомендуемый)

Язык: Kotlin



UI: Jetpack Compose (современный, реактивный)



Архитектура: MVVM + Clean Architecture, Use Cases



База данных: Room (локальное хранение)



Сеть: Retrofit + OkHttp, Kotlin Serialization / Moshi



Фоновые задачи: WorkManager (периодическая загрузка прогноза)



Карты: osmdroid (OpenStreetMap) с поддержкой офлайн-тайлов, osmbonuspack



Погодный API: OpenWeatherMap (или аналог) – бесплатный тариф



DI: Hilt



Асинхронность: Kotlin Coroutines + Flow



Геолокация: FusedLocationProvider



Фаза 1 – Инициализация проекта и управление видами рыб (CRUD)

Цель: Создать базовую структуру приложения, локальную БД и функциональность работы со справочником рыб.



Задачи:



Настройка проекта Android Studio, Gradle, зависимостей.



Реализация single activity архитектуры с навигацией (Navigation Compose).



Создание сущности Room Fish с полями:



id, name, description



optimalPressureMin/Max (гПа)



optimalWindMin/Max (м/с)



optimalTempMin/Max (°C)



season (весна, лето, осень, зима)



waterType (река, озеро, водохранилище)



isCustom (флаг пользовательской записи)



Предзаполнение БД стартовым набором распространённых видов рыб (щука, окунь, карп и т.д.) через Room Callback.



Экраны:



Список рыб (с поиском и фильтром)



Детальный просмотр характеристик



Добавление / редактирование рыбы (форма с валидацией)



Использование ViewModel + Repository + DAO для всех операций.



Результат: Пользователь может полностью управлять списком видов рыб локально.



Фаза 2 – Загрузка и хранение прогноза погоды

Цель: Интеграция с погодным API, сохранение недельного прогноза в локальной БД, отображение данных.



Задачи:



Регистрация и настройка API (OpenWeatherMap).



Создание сетевого слоя: Retrofit интерфейс, DTO модели, маппинг в доменные модели.



Создание Room сущностей:



WeatherForecast: id, timestamp, locationLat, locationLon, pressure, windSpeed, temperature, date, isCurrent, forecastType (daily/hourly).



WeatherLocation: координаты последнего запроса.



Реализация репозитория с офлайн-first стратегией: сначала чтение из БД, при наличии сети – обновление данных.



Настройка WorkManager:



Периодическая задача (например, каждые 6 часов) для обновления прогноза по сохранённым координатам.



Задача с ограничением на наличие сети (NetworkType.CONNECTED).



Экраны:



Текущая погода (давление, ветер, температура).



Недельный прогноз (список по дням).



Кнопка ручного обновления.



Получение геолокации через FusedLocationProvider для определения координат по умолчанию.



Результат: Приложение умеет скачивать и хранить недельный прогноз погоды для заданной точки, обновлять его в фоне.



Фаза 3 – Работа с картами и офлайн-режим

Цель: Отображение карты, добавление водоёмов, скачивание карт для офлайн-использования.



Задачи:



Подключение osmdroid и osmbonuspack.



Настройка карты в Compose (AndroidView).



Реализация кэширования тайлов:



Использование встроенного SqlTileWriter (хранение в SQLite) или файловой системы.



Возможность скачивания выбранной области: выбор прямоугольной области на карте, расчёт тайлов, загрузка в фоне (WorkManager) с индикатором прогресса.



Создание сущности Room WaterBody:



id, name, latitude, longitude, type (река, озеро и т.д.), description.



Экраны:



Карта с маркерами водоёмов.



Добавление водоёма долгим нажатием на карту (открытие диалога с именем и типом).



Редактирование/удаление водоёма.



Управление офлайн-областями (список скачанных регионов, удаление).



Обеспечение работы карты без интернета при наличии скачанных тайлов.



Результат: Пользователь может просматривать карту, добавлять/редактировать водоёмы, скачивать нужные области и пользоваться ими офлайн.



Фаза 4 – Алгоритм анализа клёва и экран прогноза

Цель: Связать данные о рыбе, водоёме и погоде для выдачи оценки вероятности клёва.



Задачи:



Разработка модели оценки (use case AnalyzeBiteUseCase):



Вход: объект Fish, WaterBody, текущий или прогнозный WeatherForecast.



Вычисление отклонений давления, ветра, температуры от оптимальных диапазонов рыбы.



Нормализация отклонений, применение весовых коэффициентов (например, давление 40%, ветер 30%, температура 30%).



Выход: оценка в баллах (0–100) и текстовое описание ("отличный клёв", "хороший", "средний", "слабый", "нет клёва").



Дополнительные факторы: сезон, тип водоёма (если заданы).



Экран "Анализ клёва":



Выпадающие списки для выбора рыбы и водоёма.



Отображение текущих погодных условий для выбранного водоёма (из БД).



Кнопка "Рассчитать" – вывод оценки и краткого пояснения.



Экран "Прогноз клёва на неделю":



Для выбранной пары рыба–водоём строится список по дням на основе недельного прогноза погоды.



Каждый день имеет оценку и иконку (например, рыба с разным цветом).



Сохранение истории анализов (сущность BiteAnalysisHistory) для последующего просмотра.



Результат: Основная функция приложения – прогноз клёва – полностью работает офлайн, используя локальные данные.



Фаза 5 – Дополнительные улучшения, тестирование и релиз

Цель: Повышение удобства, стабильности и подготовка к публикации.



Задачи:



Уведомления:



Настройка AlarmManager или WorkManager для проверки прогноза и отправки уведомления при высокой оценке клёва (например, >80 баллов).



Настройки включения/выключения уведомлений.



Настройки приложения:



Выбор единиц измерения (метрическая/имперская).



Периодичность обновления погоды (вручную или выбор интервала).



Управление кэшем карт (очистка).



Полировка UI/UX:



Адаптация под тёмную тему.



Анимации, улучшение навигации.



Локализация (русский, английский – по желанию).



Тестирование:



Unit-тесты для алгоритма оценки и маппинга данных.



Инструментальные тесты для Room, WorkManager.



Ручное тестирование офлайн-сценариев.



Подготовка к релизу:



Генерация подписанного APK/AAB.



Иконки, скриншоты, описание.



Политика конфиденциальности (указание использования геолокации и интернета).



Результат: Готовое к распространению приложение.



Приоритизация и зависимости

Фаза 1 обязательна – без неё невозможно тестировать анализ.



Фаза 2 и 3 можно вести параллельно, но фаза 2 нужна для фазы 4.



Фаза 4 зависит от фаз 1, 2, 3.



Фаза 5 выполняется после стабилизации основного функционала.



Рекомендуемый порядок: 1 → 2 → 3 → 4 → 5 (последовательно, как описано).



Оценка трудозатрат (приблизительно, для одного разработчика)

Фаза 1: 2–3 недели



Фаза 2: 2–3 недели



Фаза 3: 3–4 недели (сложность с офлайн-картами)



Фаза 4: 2–3 недели



Фаза 5: 2–3 недели

Итого: \~3–4 месяца.



Ключевые риски и рекомендации

Офлайн-карты: используйте osmdroid, он имеет встроенную поддержку кэша тайлов, но потребуется время на изучение. Альтернатива – MapLibre GL Native (более современный, но сложнее).



Погодный API: бесплатные тарифы часто ограничены по частоте запросов, поэтому кэшируйте данные и обновляйте не чаще одного раза в 3–6 часов.



Алгоритм оценки: начните с простой балльной системы, в дальнейшем можно доработать (например, добавить фазы луны, уровень воды).



Хранение карт: при больших областях занимает много места, предусмотрите отображение объёма и очистку.
