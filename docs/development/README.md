# docs/development

Рабочая папка процесса разработки. Здесь лежит всё, по чему ведётся работа:
требования, проектные документы, решения, задачи, фазы и карта проверок. Формат
файлов машиночитаемый — над ним работает браузерное приложение контроля процесса,
но читаются они и глазами, потому что это обычный markdown.

Папка появилась из правила [DocDD](../../app/docs/architecture/adr/0010-documentation-driven-development.md):
код меняется после документа и после подтверждения. Чтобы это правило можно было
не только объявить, но и проверять, документы должны быть связаны между собой
явно — идентификаторами, а не наличием абзаца.

## Где сейчас проект

**24.09.2026 начата новая система.** Приложение переписывается на три продукта —
Android на Kotlin, iOS на Swift, сервер на FastAPI
([A-0001](decisions/A-0001-tri-produkta-i-stek.md)).

Что это значит для этой папки:

| Записи | Состояние |
|---|---|
| Задачи прежнего плана (T-0001, T-0002, T-0005…T-0013) | сняты: план вёл к цели прежней Android-базы |
| Закрытые задачи (T-0003, T-0004, T-0014, T-0015) | остаются `done` — это история, а не план |
| Фазы P-0001…P-0004 | волны закрыты, новые появятся после M-0013 |
| Требования R-0001…R-0011 | **остаются**: они про продукт, а не про план, и переживают переписывание |
| Карты кода M-0001…M-0012 | описывают нынешнюю Android-базу; M-0012 — действующая |
| [M-0013](maps/M-0013-funkcionalnaya-karta-treh-produktov.md) | функциональная карта новой системы, ждёт подтверждения |

Порядок работ: функциональная карта → требования на её возможности → фазы →
задачи. Пока карта не подтверждена, новых задач не заводится — это то же
правило DocDD, только на уровне системы, а не одного изменения.

## Что где

| Папка | Что внутри | Префикс идентификатора |
|---|---|---|
| `requirements/` | Требования: чего система обязана достичь | `R-` |
| `design/` | Проектные документы: границы, потоки, данные, компоненты | `D-` |
| `decisions/` | Решения с причинами и отвергнутыми вариантами | `A-` |
| `contracts/` | Контракты обмена: OpenAPI, AsyncAPI, форматы файлов | `C-` |
| `tasks/` | Задачи: единица работы, которую запускают в разработку | `T-` |
| `phases/` | Фазы: группы задач с общей целью | `P-` |
| `tests/` | Карта проверок и отчёты прогонов | `V-` |
| `maps/` | Карты устройства: кодовая база, потоки данных, пользовательские пути | `M-` |
| `diagrams/` | Диаграммы отдельными файлами, если не влезли в документ | — |

`project.yaml` в корне папки объявляет проект: имя, версию контракта, пути и
роли. Приложение начинает чтение с него.

## Инструмент

Формат читает и проверяет DocDD Console — отдельный репозиторий
`D:/work/docdd-console`. Проверка без браузера, из его каталога:

```bash
npm run check -- D:\work\fishForecast
```

## Контракт формата

Контракт `docdd.workspace/1` ведёт консоль, и только она. Копия здесь отстаёт
от проверяющего инструмента — так уже было: прежняя копия не знала ни карт, ни
поля `change`, ни возврата статусов назад. Читать в репозитории консоли:

- `docs/02-workspace-contract.md` — файлы, front matter, идентификаторы,
  связи, статусы;
- `docs/05-validation.md` — проверки и коды нарушений;
- `docs/07-maps.md` — карты проекта и свидетельства;
- `docs/08-usage.md` — как этим пользоваться, в том числе импорт старой
  документации;
- `docs/schemas/` — JSON Schema.

## Отношение к app/docs

Архитектурный комплект FishForecast лежит в
[app/docs/architecture](../../app/docs/architecture/README.md) и остаётся там.
Формат этой папки — про **процесс**: кто что делает, в каком состоянии работа,
чем она проверяется. Перенос архитектурных документов сюда возможен и описан в
`docs/08-usage.md` консоли, раздел «Если документация уже написана», но это
отдельное решение, а не
побочный эффект появления формата.
