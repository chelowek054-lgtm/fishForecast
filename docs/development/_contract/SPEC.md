# Контракт файлов процесса · `docdd.workspace/1`

Формат, который читает и пишет приложение контроля процесса. Требование к
формату одно и жёсткое: **файл остаётся обычным markdown**, пригодным для чтения
и правки в редакторе, а машиночитаемость добавляется, но не заменяет текст.

Поколение схемы — `docdd.workspace/1`. Приложение отвергает незнакомое поколение
целиком, а не читает половину: правило то же, что у остальных форматов проекта.

## 1. Корень проекта

Приложение получает от пользователя путь к корню проекта и ищет
`docs/development/project.yaml`. Нет файла — проекта в формате нет, предлагается
создать или импортировать существующую документацию.

```yaml
contract: docdd.workspace/1
project:
  id: fishforecast
  name: FishForecast
  description: Офлайн-первый помощник рыболова
paths:
  requirements: requirements
  design: design
  decisions: decisions
  contracts: contracts
  tasks: tasks
  phases: phases
  tests: tests
  diagrams: diagrams
sources:
  code: [app/src]
  docs: [app/docs]
roles:
  - id: architect
    name: Архитектор
  - id: dev
    name: Разработчик
policy:
  require_approved_docs_before_dev: true
  require_verification_before_done: true
```

Пути относительны папке `docs/development`. Их можно менять — приложение не
хардкодит имена папок, оно читает манифест. `sources` объявляет, где лежит код и
старая документация: по ним строятся ссылки и работает импорт.

## 2. Файл

Каждая запись процесса — один markdown-файл с YAML front matter.

```markdown
---
id: T-0007
type: task
title: Вынести веса модели клёва в документ знаний
status: ready
owner: architect
created: 2026-08-30
updated: 2026-08-30
phase: P-07
links:
  implements: [R-0004]
  refines: [D-0003]
  decided_by: [A-0003]
  verified_by: [V-0004]
tags: [client, bite-model]
---

# Вынести веса модели клёва в документ знаний

Свободный текст: зачем, что именно делаем, чего не делаем, как понять,
что готово.
```

**Правила.**

1. Front matter — первый блок файла, между двумя строками `---`.
2. Всё, что вне front matter, принадлежит человеку. Приложение его не
   переписывает (кроме импорта, см. [import.md](import.md)).
3. Заголовок первого уровня повторяет `title`. Расходятся — предупреждение, а не
   ошибка: правит человек.
4. Кодировка UTF-8, перевод строки любой, файл заканчивается переводом строки.
5. **Даты** (`created`, `updated`) пишутся без кавычек в виде `2026-08-30`. И
   Python, и js-yaml разбирают такой скаляр в объект даты, а не в строку,
   поэтому проверка по схеме обязана сначала привести его к строке ISO-8601.
   Тонкость мелкая, но она ломает валидатор на первом же файле, если про неё не
   знать.

## 3. Идентификаторы

| Тип | Префикс | Что это | Папка |
|---|---|---|---|
| `requirement` | `R-` | Чего система обязана достичь | `requirements/` |
| `design` | `D-` | Проектный документ: границы, потоки, данные, компоненты | `design/` |
| `decision` | `A-` | Решение с причинами и отвергнутым (ADR) | `decisions/` |
| `contract` | `C-` | Контракт обмена: OpenAPI, формат файла, схема сообщения | `contracts/` |
| `task` | `T-` | Единица работы, которую запускают в разработку | `tasks/` |
| `phase` | `P-` | Группа задач с общей целью | `phases/` |
| `verification` | `V-` | Способ проверки: тест, прогон, метрика | `tests/` |

Формат идентификатора: префикс, дефис, четыре цифры (`R-0012`). Номера не
переиспользуются: удалённая запись оставляет дыру, и это правильно — ссылки на
неё не должны вдруг указать на другое.

Имя файла: `<id>-<короткий-слаг>.md`, например `T-0007-bite-model-document.md`.
Слаг для человека, идентификатор для машины; переименование слага ничего не
ломает.

## 4. Связи

Связи задаются только через `links`, только идентификаторами и только в одну
сторону — обратные строит приложение.

| Связь | От кого | К кому | Смысл |
|---|---|---|---|
| `implements` | task | requirement | Задача выполняет требование |
| `refines` | design, task | design, requirement | Уточняет, не отменяя |
| `decided_by` | design, task | decision | Опирается на принятое решение |
| `supersedes` | любой | тот же тип | Заменяет собой прежнюю запись |
| `depends_on` | task | task | Не начинать раньше, чем закончится та |
| `blocks` | task | task | Обратная сторона зависимости, выводится сама |
| `verified_by` | requirement, task | verification | Чем проверяется |
| `verifies` | verification | requirement, task | Что проверяет |
| `documents` | task | design, contract | Какой документ правится этой задачей |
| `covers` | phase | task | Состав фазы |

Ссылка на несуществующий идентификатор — ошибка формата. Циклы в `depends_on` —
ошибка. Всё остальное приложение показывает как предупреждение.

## 5. Ссылки на код и внешние документы

Внутри текста — обычные markdown-ссылки. Приложение понимает три вида:

- на файл процесса: `[T-0007](../tasks/T-0007-bite-model-document.md)`;
- на код проекта: `[CalculateFishActivityUseCase.kt](../../../app/src/main/java/...)`
  — путь от корня проекта, приложение проверяет существование;
- на строку кода: тот же путь с `#L120`.

Ссылка на несуществующий файл кода — предупреждение: код мог переехать, и это
повод поправить документ, а не сломать сборку.

## 6. Диаграммы

Два способа, оба обязаны поддерживаться:

1. **Внутри документа** — блок ```` ```mermaid ````. Так лучше для схем, которые
   объясняют текст рядом.
2. **Отдельным файлом** — `diagrams/<имя>.mmd`, вставляется ссылкой:
   `![Потоки данных](../diagrams/dataflow.mmd)`. Так лучше для схем, которые
   используются в нескольких документах.

Приложение рисует и то, и другое. Ошибка разбора диаграммы — предупреждение у
документа, а не отказ его показывать.

## 7. Проверки и тесты

Запись типа `verification` описывает **способ** проверки, а не её результат:

```yaml
id: V-0004
type: verification
title: Подмена документа модели меняет расчёт
kind: unit          # unit | integration | manual | metric | review
runner: gradle      # чем запускается; для manual — пусто
command: ":app:testDebugUnitTest --tests *BiteModelTest*"
verifies: [R-0004]
```

Результаты прогонов кладутся в `tests/reports/` файлами
`<дата>-<runner>.json` в формате:

```json
{
  "contract": "docdd.workspace/1",
  "runner": "gradle",
  "started_at": "2026-08-30T10:00:00Z",
  "total": 161,
  "failed": 0,
  "verifications": { "V-0004": "passed", "V-0007": "failed" }
}
```

Отчёты — производные данные: их можно удалить, и формат не сломается.
Приложение показывает по ним, какие требования подтверждены фактом, а какие
только объявлены.

## 8. Что делает формат проверяемым

Не «есть документация», а «связи сходятся». Приложение считает четыре вещи:

1. **Требование без проверки** — объявлено, но никем не подтверждается.
2. **Задача без требования** — работа, которая никому не понадобилась.
3. **Задача в работе с неутверждённым документом** — прямое нарушение DocDD.
4. **Документ, изменённый позже задачи, которая его правила** — расхождение,
   которое стоит объяснить.

Первые три — правила процесса, описанные в [lifecycle.md](lifecycle.md).

## 9. Совместимость

- Незнакомые поля front matter сохраняются при записи и игнорируются при чтении.
  Проект вправе добавить своё.
- Незнакомый тип записи — предупреждение, файл показывается как есть.
- Смена поколения контракта (`docdd.workspace/2`) означает несовместимость и
  требует явной миграции.
